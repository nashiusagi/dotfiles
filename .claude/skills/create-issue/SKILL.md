# Create Issue

ユーザーの要望をもとに調査を行い、GitHub issueを起票するワークフロー。

---

## Step 1: 要望を把握する

ユーザーが何を実現したいのかを理解する。曖昧な場合はひとつだけ質問して明確にする。
調査に十分な情報があれば、すぐ次のステップへ進む。

---

## Step 2: 調査する

サブエージェントを使って並列で調査する。調査する観点：

- **実現方法**: 主要なツール・ライブラリ・プラグインの候補
- **比較**: 各候補のメリット・デメリット、メンテナンス状況
- **依存関係**: インストール方法（apt, npm, cargo など）
- **既存設定との兼ね合い**: dotfilesで現在使っているものと競合しないか
- **得られるユーザー体験**: 実装後に何が便利になるか

現在のdotfilesの関連設定も確認し、「現状」と「移行後」の差分が明確になるよう調査する。

---

## Step 3: issueを起票する

調査完了後、ユーザーに確認せず即座に `gh issue create` で起票する。
リポジトリは現在のディレクトリの git リポジトリを使う。

```bash
gh issue create --title "feat: {内容}" --body "..."
```

### issueの構成

```markdown
## 背景

なぜこれをやるのか。現状の問題点や、今使っているものの課題があれば記載する。

## やること

- 具体的な変更内容（ファイル名・コードスニペット含む）

## 得られるユーザー体験

- 実装後に何が便利になるか（箇条書き）

## 比較（選択肢が複数ある場合）

| 項目 | 選択肢A | 選択肢B |
|------|---------|---------|
| ...  | ...     | ...     |
```

### 書き方のポイント

- タイトルは `feat: {動詞}+{内容}` 形式（例: `feat: delta を導入して git diff を見やすくする`）
- 「やること」には実際のコードスニペットを入れると実装者が迷わない
- 比較表は選択肢が2つ以上あるときだけ入れる。明らかに一択なら省略してよい
- ユーザー体験は「〜できる」「〜が一目でわかる」など具体的に書く

---

## 注意

- 起票前にユーザーへの確認は不要。調査して即起票する
- ただし調査中に方針を左右する不明点があればユーザーに聞く
- issueはあくまで「何をするか」の記録。実装はしない
